\subsection{Requirements that guide the selection}

The application must automate the \textbf{collection}, \textbf{processing}, \textbf{analysis} and \textbf{visualization} of YouTube data. The scope includes (1) a \textbf{data collection module} that retrieves video comment data from YouTube Data API, (2) an \textbf{AI query model} (Natural Language Interface) that translates informal user requests into valid YouTube Data API queries using a \textbf{pre-trained AI model}, (3) a \textbf{data processing pipeline} to clean, normalize, validate and structure raw API responses and (4) a \textbf{presentation layer} with charts for visualization.

From an architectural point of view, the system must follow these principles: a backend built with a \textbf{modern web framework} and a \textbf{relational database}, a frontend served as static assets by a lightweight \textbf{web server} and full \textbf{containerization} for reproducible deployment.

Finally, the project explicitly excludes training or fine-tuning NLP models; it integrates \textbf{existing}, \textbf{pre-trained models} for query translation.

\subsection{Selected technology stack}

Based on the requirements above, the selected stack is:

\begin{itemize}
    \item Backend framework: Django REST Framework (DRF).

    \item Database management: PostgreSQL.

    \item Frontend framework: React.

    \item Frontend tooling: Vite (build tool and development server).

    \item Web server / reverse proxy: Nginx.

    \item Application server: Gunicorn, a production application server for a WSGI-based Django deployment.

    \item Containerization: Docker.
\end{itemize}

\subsection{Justification of the selection}

\subsubsection{Backend (Django + DRF)}

\textcite{django_framework} describes Django as a \enquote{high-level Python web framework focused on rapid development and pragmatic design}, which aligns with the need to implement the system's core modules in an organized way. In turn, Django REST Framework is a toolkit for building Web APIs and provides features such as request handling, authentication, serialization and API documentation support, making it suitable for the separation between frontend and backend services \autocite{drf_framework,drf_requests,drf_authentication,drf_documenting_api}.

For the data collection layer, the system uses direct HTTP requests to interact with the YouTube Data API. This approach is suitable because the API exposes structured resources in JSON format and uses explicit request parameters to define the data to be retrieved. In particular, parameters such as \texttt{part}, \texttt{fields}, \texttt{maxResults} and \texttt{pageToken} are central to controlling response size, pagination and quota usage. Therefore, direct HTTP integration supports a transparent and reproducible implementation, since the request URLs, parameters, response payloads and error handling logic remain visible in the source code \autocite{youtube_data_api_docs}.

\subsubsection{Database (PostgreSQL)}

The scope~\ref{chap:project_scope} requires a relational database for data storage. PostgreSQL is selected because it is an open-source object-relational database system with strong support for structured schemas and relationships, which is useful storing comments, replies, projects and saved queries \autocite{postgresql_about}.

\subsubsection{Frontend (React + Vite)}

The scope~\ref{chap:project_scope} expects a frontend built with a modern JavaScript framework and explicitly lists React as an example option. React is selected for the presentation layer because it is based on reusable UI components, which fits the development of an interactive web interface with charts \autocite{react_describing_ui}. Vite complements this choice because it is a build tool designed to provide a faster and leaner development experience and to generate optimized static assets for production deployment \autocite{vite_getting_started}.

\subsubsection{Web server and deployment}

The scope~\ref{chap:project_scope} states the use of a lightweight server such as \textbf{Nginx} to serve static frontend assets. Nginx is also suitable as a reverse proxy in front of the backend application server. Nginx is suitable for this architecture because it can serve static content and operate as a reverse proxy in front of the backend service \autocite{nginx_serving_static_content,nginx_reverse_proxy}. For the backend deployment, Gunicorn is selected as the application server because it is a Python WSGI HTTP server and Django projects already provide a WSGI entry point for this deployment model \autocite{gunicorn_homepage,gunicorn_quickstart}. Finally, Docker is used to containerize all services in order to support consistent and reproducible deployment across environments \autocite{docker_overview}.

\subsubsection{LLM API integration approach}

The query translation component calls a hosted LLM through the OpenAI Responses API, constrained by a strict JSON schema through the Structured Outputs feature \autocite{openai_structured_outputs}. As with the YouTube Data API, the request is a direct HTTP call made with the Python standard library, so no vendor SDK is added. The model is a configuration value (\texttt{LLM\_MODEL}, \texttt{gpt-5.6-luna} by default) that can be changed without modifying code. A hosted model is used instead of a locally executed one because the scope excludes training or fine-tuning models and because it keeps the deployment free of GPU requirements.

To support transparency and reproducibility, the backend also stores the generated query parameters, the model name, the prompt version and timestamps, because API-based data collection can vary over time and requires consistent documentation of conditions.

\subsubsection{Practical considerations and alternative stacks}

This application could also be implemented with other mainstream stacks. However, this specific stack is selected because it matches the architecture principles defined in the project scope, relies on widely used open-source technologies that other students and researchers can maintain, and reduces implementation risk because the author was already familiar with them.

\subsection{Resulting architecture}

Figure~\ref{fig:architecture} shows how the selected technologies are combined in the application. The five services run as Docker Compose containers. Nginx is the single entry point for the browser: it forwards the requests under \texttt{/api/} to the backend and every other request to the frontend. The backend code is the only code that reaches the database, and the \texttt{api} service is the only one that reaches the external APIs; it contains the data collection and the processing and analysis components of objective~\ref{obj:design}; the visualization component is the React frontend, which reads the results through the backend API. A started collection run is executed by a background thread of the \texttt{api} service after the request that started it has been answered, and the \texttt{purge} service, built from the same image, runs the 30-day purge every hour (Activities~\ref{act:2.1} and~\ref{act:3.2}).
