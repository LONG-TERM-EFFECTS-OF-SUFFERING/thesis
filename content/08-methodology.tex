\chapter{Methodology}

Scrum is an agile framework for iterative and incremental development in which work is broken into goals completed within time-boxed iterations called sprints, typically lasting two to four weeks \autocite{schwaber2020scrum}. This project adopted an adapted Scrum framework to guide the software development process. While Scrum is traditionally designed for team-based development, this thesis applied the Scrum artifacts and events that provide particular value for individual academic software projects, especially in maintaining transparency and systematic progress tracking.

The choice of Scrum was motivated by two primary factors: its \textbf{flexibility} through iterative development and its emphasis on \textbf{structured documentation} through artifacts. This aligned well with the exploratory nature of thesis development, where requirements may evolve as the research progresses.

\section{Scrum artifacts adapted for this project}

\subsection{Product backlog}

The product backlog serves as an emergent, ordered list of what is needed to improve the product and functions as the single source of work for the project \autocite{schwaber2020scrum}. For this thesis, the \textbf{product backlog} documents all planned features, technical requirements and improvements for the web application. This artifact provided transparency in planning and allowed development tasks to be prioritized by their contribution to the thesis objectives.

\subsection{Sprint backlog}

Composed of the \textbf{sprint goal}, selected \textbf{product backlog} items and an actionable plan for delivering an increment \autocite{schwaber2020scrum}, the \textbf{sprint backlog} of each development iteration was its share of the sprint plan described below: a goal and the product backlog items assigned to it. For this individual project, sprints were two-week periods during which specific functionality was developed and integrated into the application.

\section{Scrum events adapted for this project}

Scrum events are designed for team collaboration and recur in every sprint; this project held sprint planning once, at the start, and replaced the retrospective.

\subsection{Sprint planning}

Sprint planning determines what can be delivered in a sprint and how that work will be achieved \autocite{schwaber2020scrum}. In this project it was done once, before the first sprint: a single plan distributed the \textbf{product backlog} items across all thirteen sprints, with a \textbf{sprint goal}, dates and an estimate in points for each. The plan is kept in the sprint planning document described in Chapter~\ref{chap:development}.

\subsection{Sprint retrospective}

The sprint retrospective provides an opportunity to plan ways to increase quality and effectiveness \autocite{schwaber2020scrum}. In this project, retrospectives were not held as separate events at the end of each sprint. The inspection they provide happened at the level of each user story instead: every story ended with a structured review whose findings were fixed, deferred or returned to the plan (Section~\ref{sec:ai_assisted_workflow}), and problems that the reviews found more than once were added to the instructions the AI agent reads before every story, so later stories avoided them.

Although Scrum is traditionally conceived as a framework for teams, with defined roles including \textbf{Scrum master}, \textbf{product owner} and \textbf{developers} \autocite{schwaber2020scrum}, this project adapted its core principles to the context of individual thesis development. The emphasis remained on the empirical pillars of \textbf{transparency}, \textbf{inspection} and \textbf{adaptation} \autocite{schwaber2020scrum}, which are particularly valuable for maintaining rigor and documentation in academic software development projects.

\section{AI-assisted development workflow}
\label{sec:ai_assisted_workflow}

The software was implemented with the BMAD Method \autocite{bmad_method}, an open-source framework that organizes software development with AI agents around explicit planning artifacts, and with Claude Code \autocite{claude_code}, an AI coding agent developed by Anthropic. BMAD did not replace the adapted Scrum framework: it operated inside each sprint, at the level of a single user story.

The product backlog remains the source of requirements. BMAD mirrors it as a ticket tree with one initiative for the application, one epic per backlog epic and one story per user story, each citing the backlog identifiers it covers. Every story followed the same cycle:

\begin{enumerate}
    \item \textbf{Plan.} The agent drafts a plan with the problem, the approach, the constraints that must always or never hold and a matrix of expected behavior for normal and edge cases. The author reviews and approves it; from then on the approved intent is frozen and changes only through an explicit renegotiation recorded in the plan.

    \item \textbf{Implement.} The agent implements the plan, with its tests, on a branch named after the user story.

    \item \textbf{Review.} A structured review compares the change with the plan. Each finding is fixed before the story closes, recorded in a shared deferred-work log or returned to the author as a problem with the plan.

    \item \textbf{Verify and document.} The backend and frontend test suites, the migration check and the production build run before the story closes, and a beginner-oriented explanation of the reviewed code is added to the project documentation.
\end{enumerate}

In this cycle the author acts as product owner and technical reviewer: defining and approving the intent of each story, deciding every deferred or ambiguous item, reviewing the changes and merging them. The plans, the review logs, which record how each finding was classified and resolved, and the deferred-work log are kept in the repository, so every development decision can be inspected later, as every collection request can. Because generated tests can pass for the wrong reason, a test was trusted only after the code it covers had been broken on purpose, for example by removing the check under test, and the test had been seen to fail; the code was then restored.
