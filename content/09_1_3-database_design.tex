\subsection{Database design}

The database was designed for the PostgreSQL DBMS selected in Activity~\ref{act:1.1} and for the Django-based backend defined in the technology stack. The schema supports the complete workflow of the application: project creation, query definition, YouTube data collection, API request traceability, data processing and visualization. In this design, Django model classes define the application entities and the ORM maps them to PostgreSQL tables, so the database structure remains close to the backend implementation.

The design also responds to Activity~\ref{act:1.3}, which requires storage for videos, comments, replies, user projects, API queries and processing metadata. For methodological transparency, the schema does not only store the final processed data. It also stores collection runs, request parameters, quota consumption, pagination information, raw API payloads and processing outputs, because these records describe the conditions under which the dataset was obtained and transformed. Raw payloads and every other record that holds YouTube API data are kept for at most 30 days after retrieval, as required by the YouTube API Services Developer Policies \autocite{youtube_api_services_developer_policies}; collection and processing metadata are kept permanently.

Figure~\ref{fig:er_diagram} shows the entity-relationship diagram; the complete table definitions, with every field and data type, are in \href{https://github.com/LONG-TERM-EFFECTS-OF-SUFFERING/thesis/tree/main/docs/database_schema.md}{\texttt{database\_schema.md}}. The following sections summarize the design criteria, implementation model, main entities and integrity controls of the database schema.

\subsubsection{Design criteria}

The schema was defined using the following criteria:

\begin{itemize}
    \item Preserve \textbf{traceability} of each collection session through explicit records of the effective query, execution time, API endpoints, request parameters, quota consumption and pagination tokens.

    \item Store YouTube resources in a \textbf{normalized relational structure} that separates channels, videos, comments, request logs, processing outputs and project management data.

    \item Represent \textbf{replies} in the same table as top-level comments using a self-reference, instead of creating a duplicated table structure for replies.

    \item Support \textbf{reproducibility} by keeping original YouTube identifiers and raw JSON payloads for the 30-day retention window, and query parameters, timestamps and processing metadata permanently.

    \item Support later \textbf{analysis and visualization} through normalized comment text, sentiment results, processing reports and stable relationships between projects, collection runs, videos and comments.
\end{itemize}

\subsubsection{Implementation model}

The current model uses Django's built-in authentication user through \texttt{settings.\allowbreak AUTH\_\allowbreak USER\_\allowbreak MODEL}. With Django's default configuration, this means that user accounts are stored in \texttt{auth\_user}, not in a custom table. Application-specific entities use UUID primary keys generated by Django, while foreign keys that point to the user model follow the primary key type of the configured Django user.

PostgreSQL \texttt{JSONB} columns are represented in Django with \texttt{JSONField}. These fields are used when the application must store flexible data whose structure may vary between requests, such as structured query parameters, raw API responses, request payloads and summary outputs. Timestamp columns such as \texttt{created\_at} and \texttt{updated\_at} are maintained by Django using automatic timestamp fields. Enumerated values such as statuses, query sources, comment levels and sentiment labels are represented with Django choices; statuses and sentiment labels are also enforced in PostgreSQL with check constraints, so a value written outside the application cannot bypass them.

\paragraph{User and project management}

Each research project belongs to one owner. A saved query keeps the original natural language prompt (if there was one), the query source, the date, regional and language filters, the number of videos to discover and of comments and replies to collect, the structured query parameters and, when the query was generated by an LLM, the model metadata. This connects the user-facing query process with the exact parameters later sent to the YouTube Data API.

\paragraph{Collection traceability}

When a collection run starts, the parameters of the saved query are copied into \texttt{effective\_\allowbreak params} and the comment and reply limits into \texttt{requested\_\allowbreak comment\_\allowbreak limit} and \texttt{requested\_\allowbreak reply\_\allowbreak limit}, and none of them is edited afterwards. A later change to the saved query, or its deletion, therefore does not alter the record of what a past run requested. Each request of the run is stored in \texttt{api\_request\_logs} with its sequence number, endpoint name, request parameters, \texttt{part} and \texttt{fields} values, pagination tokens, HTTP status, quota cost, number of returned items and possible errors, so the collection process is auditable instead of a black box. The counter \texttt{total\_\allowbreak videos\_\allowbreak skipped} records search results that added no video, such as repeated video identifiers or channel and playlist results, so the discovered, skipped and collected counts can be reconciled.

\paragraph{YouTube resources}

Original YouTube identifiers are unique business keys, while UUID values are used internally for relationships. Because the same video or comment can be found by several runs, \texttt{collection\_\allowbreak run\_\allowbreak videos} and \texttt{collection\_\allowbreak run\_\allowbreak comments} link them to each run, recording the result page and discovery time and, for comments, the position within the thread. Statistics are stored in \texttt{video\_\allowbreak statistics\_\allowbreak snapshots} rather than in \texttt{youtube\_videos} because views, likes and comment counts change over time. Replies are stored in \texttt{youtube\_comments} together with top-level comments, through the self-referential key \texttt{parent\_\allowbreak comment\_\allowbreak id}. Channels, videos and comments record their last retrieval time in \texttt{last\_\allowbreak fetched\_\allowbreak at}, which starts the 30-day retention window.

\paragraph{Processing and analysis}

The table \texttt{processing\_runs} holds two kinds of run. A normalization run cleans the text of the collected comments and writes \texttt{text\_\allowbreak normalized}; its report stores the version of the normalization rules, the number of inputs, written rows and errors, and how many comments each rule changed. A sentiment run classifies the comments after a completed normalization run; its report stores the model name and version, a count per sentiment label and the number of comments skipped for having no text. Both reports hold counts only, without comment text or YouTube identifiers. Each row of \texttt{comment\_sentiments} stores the model name and version next to the label, score, confidence, language code and raw model output, so results from different versions of the same model are never mixed.

The initial design also included a \texttt{derived\_metrics} table for aggregated values, which was not implemented. Summaries and the sentiment distribution are computed from the stored rows on request, using database aggregation, so they always reflect the data that remain after the purge and need no retention rule of their own.

\subsubsection{Integrity and reproducibility controls}

Several integrity controls are enforced by PostgreSQL. Unique constraints prevent duplicate project names per user, duplicate query names for the same creator within a project, duplicate external YouTube identifiers, duplicate video links within the same collection run, duplicate comment links within the same collection run, more than one statistics snapshot per video in the same collection run and more than one sentiment result per comment, model and model version in the same processing run. The request log sequence is unique inside each collection run, so the request order can be reconstructed. Check constraints restrict project, collection run and processing run statuses and sentiment labels to their allowed values, keep sentiment scores between $-1$ and $1$ and confidence values between $0$ and $1$, require the comment level to match the presence of a parent comment, and ensure that the finish timestamp of a collection run, an API request or a processing run is not earlier than its start. The date range of a saved query is validated by the API before the query is saved, but it is not a database constraint.

The reproducibility controls are equally important. Collection tables store the exact request parameters, quota costs and pagination tokens used to obtain the data. YouTube resource tables keep the original platform identifiers and raw payloads for 30 days after retrieval; a purge command then deletes them, cascades the deletion to statistics snapshots, run links and sentiment records and stamps the collection run with \texttt{data\_\allowbreak purged\_\allowbreak at}. Processing tables store model names and versions, the version of the normalization rules, summary reports and raw model output. Together, these records allow a later reviewer to understand not only what data were collected, but also how the data moved from API requests to stored records and analytical results. After the purge, the collection and processing records remain as the documented procedure that can be repeated.

\paragraph{Ethical and privacy controls}

In accordance with Colombian Statutory Law 1581 of 2012 \autocite{ley1581_2012} and the YouTube API Services Developer Policies \autocite{youtube_api_services_developer_policies}, author channel identifiers (\texttt{author\_channel\_id}) and comment text are used only within internal database relations, and the only analytical values stored as records are the counts in processing reports, which contain no comment text, author identifier or YouTube resource identifier. This prevents the construction of individual behavioral profiles. Comments, author identifiers and the sentiment results computed from them fall under the 30-day retention window, so no personal data from YouTube remains in the database after the purge.
