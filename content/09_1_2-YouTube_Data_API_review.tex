This section is based primarily on the official YouTube Data API documentation provided by Google for developers \autocite{youtube_data_api_docs}, which is the main source for the functionality, endpoints, request parameters, quota management and limitations described below.

\subsection{Functionality and general overview}

The YouTube Data API v3 is the official interface provided by Google for accessing and, in some cases, managing YouTube data from external applications. It exposes structured resources in JSON format through resource-specific methods such as \texttt{list}, \texttt{insert}, \texttt{update} and \texttt{delete}, depending on the type of resource and the permissions required \autocite{youtube_data_api_docs}.

To use the API, developers must create a Google project, enable the YouTube Data API and provide valid credentials with each request. Requests for public data can be made with an API key, while requests that modify data or access private user information require OAuth 2.0 authorization. Every request also consumes quota, so requests must be designed carefully, especially in research-oriented data collection workflows \autocite{youtube_data_api_docs}.

\subsection{Available endpoints and methods}

The YouTube Data API v3 is organized by resource type rather than as a single generic endpoint, and each resource exposes the methods supported for that entity. This project uses only read-oriented methods: those that discover videos, retrieve video metadata, collect top-level comments and retrieve replies, summarized in Table~\ref{tab:youtube_api_core_resources}. Channel metadata is also retrieved, through \texttt{channels.\allowbreak list}, but only as context for the videos; channel-level audience analysis is outside the scope of this thesis and is left for future work.

\subsection{Parameters}

The YouTube Data API v3 relies on query parameters to define both the subset of resources to retrieve and the amount of information returned in each response. Partial resource retrieval is mandatory: the \texttt{part} parameter specifies which top-level sections of a resource are included in the response, and the optional \texttt{fields} parameter restricts it further to the nested properties required by the application, which reduces network transfer, parsing and storage overhead \autocite{youtube_data_api_docs}.

Some parameters identify the target resource set, such as \texttt{q}, \texttt{id}, \texttt{videoId} and \texttt{parentId}; others control the number, order, temporal range, region and language of returned items, such as \texttt{maxResults}, \texttt{pageToken}, \texttt{order}, \texttt{publishedAfter}, \texttt{publishedBefore}, \texttt{regionCode} and \texttt{relevanceLanguage}. Some methods also impose exclusive filter rules: \texttt{commentThreads.\allowbreak list} requires exactly one filter such as \texttt{videoId}, \texttt{id} or \texttt{allThreadsRelatedTo\-ChannelId}, while \texttt{comments.\allowbreak list} requires either \texttt{id} or \texttt{parentId}. These rules constrain how requests can be generated automatically from user input. Table~\ref{tab:youtube_api_parameters} summarizes the parameters relevant to the application \autocite{youtube_data_api_docs}.

\subsection{Quota management}

The YouTube Data API v3 uses a quota system to regulate service usage and protect platform resources. Projects that enable the API receive a default allocation of 10,000 quota units per day. Every request consumes quota, including invalid requests, which still cost at least one unit, and each additional page of a multi-page result costs the method's quota again. Quota management is therefore a methodological consideration as well as a technical one, because it bounds how much data a study can collect per day \autocite{youtube_data_api_docs}.

Most read methods relevant to the project cost one unit, but \texttt{search.\allowbreak list} costs 100 (Table~\ref{tab:youtube_api_quota_costs}), so repeated exploratory searches exhaust the daily quota much faster than metadata retrieval or comment collection. The collection workflow should therefore minimize redundant \texttt{search.\allowbreak list} calls, reuse identifiers already retrieved, switch to the one-unit methods once the target resources are identified and document the exact parameters and timestamps of each collection session. Additional quota can be requested from Google, but only after a compliance audit against the YouTube API Services Terms of Service, so efficient request design is the first strategy for quota management and quota extension a secondary measure \autocite{youtube_data_api_docs}.

\subsection{Documented limitations}

This application depends on an external platform whose methods, parameters, quota costs and usage policies may change over time, and every YouTube collection tool, whether open-source or commercial, shares this dependency on an interface that Google can modify unilaterally and without academic input. The revision histories of the Data API and of the YouTube API Services Terms and Policies record such changes \autocite{youtube_data_api_revision_history,youtube_api_services_developer_policies}. For example, the quota cost of \texttt{search.\allowbreak list} was changed to 100 units, which directly affects collection strategies based on repeated search requests, and the discontinuation of the \mintinline{text}{relatedToVideoId} parameter in August 2023, previously essential for expanding datasets through recommendation networks, prevents the replication of earlier studies that relied on it.

The developer policies also limit storage. Because OpenTube authenticates with an API key, the data it receives may be stored for no longer than 30 calendar days and must otherwise be refreshed or deleted, with no exemption for academic use \autocite{youtube_api_services_developer_policies}. The raw response payloads (\texttt{raw\_payload}) needed to verify analytical transformations therefore exist only within that window; the resulting retention policy is described in Subsection~\ref{subsec:ethics_privacy_and_terms_compliance}.

Search results are also neither fully explained nor stable. The official documentation states that \texttt{order=relevance} is the default behavior of \texttt{search.\allowbreak list}, but it does not explain the ranking logic, so it is difficult to explain why certain videos are returned before others. \textcite{efstratiou2025youtube} audited the Search endpoint by running identical queries at 5-day intervals over 12 weeks across six diverse topics and found that the Jaccard similarity between the returned video sets declined substantially over time: the same query may yield very different datasets depending solely on when it is executed. For this reason, the present project treats API-based retrieval as a constrained observation of the platform rather than as a complete or stable representation of all relevant YouTube content.

Given this temporal decay and the 30-day retention limit, end-to-end computational reproducibility, defined as generating identical datasets from live API queries over time, is unachievable on YouTube. This work therefore adopts a two-tiered methodological framework: (1) \textbf{auditability and documented provenance} during data collection, achieved by permanently logging request parameters, pagination tokens and execution timestamps (\texttt{api\_request\_logs}, \texttt{collection\_runs}) and by retaining raw payloads for the 30 days permitted by the YouTube API Services Developer Policies; and (2) \textbf{computational reproducibility} during analysis, obtained by applying deterministic parsing routines and documented sentiment models to the raw data while it is retained. The reproducible unit in OpenTube is thus the documented collection procedure (saved query, effective parameters and request logs) rather than the dataset itself, because that procedure is what another researcher can verify and repeat.
