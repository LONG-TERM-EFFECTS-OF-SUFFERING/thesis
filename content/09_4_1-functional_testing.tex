This activity covers user stories US-033 to US-036; the presentation smoke tests of US-037 were not completed. Each component was tested on its own with controlled data, and the tests are part of the source code, so any reader can run them again: \texttt{python manage.py test} for the backend and \texttt{npm test} for the frontend.

\subsection{Test design}

Four rules were applied to every test:

\begin{itemize}
    \item \textbf{No live services.} No test contacts the YouTube Data API or the OpenAI API. Services that call them receive the network function as a parameter, and the end-to-end tests replace only Python's \texttt{urlopen}, so the real code that builds URLs, sets timeouts, decodes responses and maps errors is exercised.

    \item \textbf{Documented shapes.} Fake responses follow the structure documented for each API, including pagination tokens and error bodies such as \texttt{quotaExceeded}, and the identifiers and texts are invented.

    \item \textbf{Exact expectations.} Results are compared as whole values, not by searching for a substring, after a test was found that passed because the expected text was already part of its input.

    \item \textbf{Tests that can fail.} A test was accepted only after the behavior it covers was broken on purpose and the test failed, as described in Section~\ref{sec:ai_assisted_workflow}. Fake services also raise an error when they receive an unexpected request, so a defect that repeats requests ends the test instead of hanging it.
\end{itemize}

The tests also found defects in code that had already been reviewed. \subsection{Frontend tests}

The frontend suite contains 148 tests, run with Node.js's built-in test runner. They cover the logic that the interface depends on, extracted into plain TypeScript modules: building the saved-query request from the form, applying a draft and converting dates between UTC and local time, under a fixed non-UTC time zone so that a confusion between the two cannot pass; merging and discarding responses for the active project; sentiment formatting and distribution; filter parsing; the detection of active and finished runs that drives the automatic reload; the login requests; navigation, theme and interface language, including a check that every Spanish translation keeps the placeholders of its English text. The API client functions are tested with a stubbed \texttt{fetch}, including the runtime checks that reject a response whose shape differs from the expected one.

The components themselves are not rendered by any test, because the project has no browser test environment; the forms, tables and chart were verified manually during each story and, on the real validation data, in a headless browser (Appendix~\ref{chap:annex_screens}). Automated rendering tests, planned as US-037, were not completed and remain future work.
