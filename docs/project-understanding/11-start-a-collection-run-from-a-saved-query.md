# 11 - Start a collection run from a saved query

Story: US-011, Start a collection run from a saved query.

Status note: this document describes the US-011 implementation **after** the code review of 2026-10-05. The review led to no code changes; its two findings were deferred or rejected (see Known gaps).

## What this story added

US-010 gave the app a `CollectionRun` record but no way to create one. This story adds that way:

- a **"Start run"** button on each saved query card in the UI.

- an endpoint behind it: `POST /api/projects/<project_id>/queries/<query_id>/runs/`.

- a new column on `collection_runs`, `effective_params`, holding a **copy** of the parameters the run uses.

Starting a run creates the record in `pending` and returns it. Nothing calls YouTube yet. US-015 adds the collector that picks up a `pending` run and moves it to `running`.

## Why this matters

The thesis says the reproducible unit is the documented procedure: "saved query, effective parameters and request logs". A run must therefore answer:

```text
Exactly which parameters did this run use?
```

The saved query alone cannot answer that. A saved query can be deleted, which empties the run's `saved_query` link (`SET_NULL`, from US-010), and it could be edited in the admin after the run. So the run keeps its own copy.

## Key concept: a snapshot, not a reference

A **reference** says "go look at saved query X". A **snapshot** says "here is what saved query X said at the moment the run started".

`effective_params` is a snapshot:

```json
{
  "search_list": {"part": "snippet", "type": "video", "q": "movilidad Cali", "maxResults": 50},
  "max_videos_to_discover": 250
}
```

- `search_list` is the query's `structured_query_params`: the parameters that go to YouTube's `search.list`.

- `max_videos_to_discover` is the run's overall cap. It is not a `search.list` parameter, so it sits beside that object rather than inside it. US-015 uses it to decide when to stop paging.

Saving the run writes this dictionary into its own PostgreSQL `JSONB` value. Later changes to the saved query cannot reach it.

## Key concept: re-validate at the moment of use

The query's parameters were validated when it was saved (US-009). The endpoint still runs `validate_search_parameters` again before creating the run. A row can change after it was saved, for example through the admin, and a run should never record parameters YouTube would reject. If there are findings, the response is `400` with the same message list a rejected save returns, and no run is created.

## Key concept: the project comes from the query

The URL names both the project and the query. The view looks the query up **inside** that project, among the queries the current owner created. A query from another project or another owner is a `404`, the same answer as a query that does not exist. That way an outsider learns nothing about other people's data, and the run's `project` always matches its query's project.

## File-by-file explanation

### `src/api/core/models.py`

Adds `effective_params = models.JSONField(default=dict)` to `CollectionRun`. `transition_to` and the constraints are unchanged.

### `src/api/core/migrations/0005_collectionrun_effective_params.py`

Generated by `makemigrations`. Adds the column.

### `src/api/core/serializers.py`

`CollectionRunSerializer` turns a run into JSON. Every field is read-only: runs are created by the start view, never by a client sending a run body.

### `src/api/core/views.py`

`CollectionRunStartView.post` performs four steps: find the owner's query in the owner's project (or `404`), validate its parameters (or `400`), create the run with the snapshot, and return `201` with the serialized run.

### `src/api/core/urls.py`

Routes `projects/<uuid:project_id>/queries/<uuid:query_id>/runs/`, named `project-query-run-start`.

### `src/api/core/admin.py`

`effective_params` is read-only in the admin, so the snapshot can be seen but not edited.

### `src/api/core/tests.py`

`CollectionRunStartApiTests` covers starting a run, the snapshot surviving an edit and a delete of the query, foreign and unknown ids returning `404`, and invalid stored parameters returning `400`.

### `src/ui/src/apiClient.ts`

`startCollectionRun(projectId, queryId, signal)` sends the POST. `isCollectionRun` checks the response shape before the rest of the UI trusts it.

### `src/ui/src/App.tsx`

Each query card gets a button and a status line. The state is a dictionary keyed by query id, so each card tracks its own request. Two guards stop duplicate runs: the button is disabled while its request is in flight, and `handleStartRun` returns early if that query already has a request running. The second guard catches a double click that lands before React re-renders the disabled button.

### `src/ui/tests/collectionRunApi.test.ts`

Tests the client with a stubbed `fetch`: the URL and method, a `404` error message, and a malformed response.

## How the pieces connect

```text
Saved query card --"Start run"--> startCollectionRun()
                                      |
                POST /api/projects/<p>/queries/<q>/runs/
                                      |
                        CollectionRunStartView.post
                          |-- owner's query in owner's project? else 404
                          |-- validate_search_parameters? else 400
                          '-- CollectionRun.objects.create(
                                 status=pending,
                                 effective_params={search_list, max_videos_to_discover})
                                      |
                              201 + run JSON --> card shows "Run pending"
```

## How to test manually

1. Run the app, choose a project and save a query.

2. Click **Start run** on its card. The button reads "Starting…" briefly, then the card shows `Run pending`.

3. Open `/admin/`, go to Collection runs and open the new run. `effective_params` shows the snapshot and cannot be edited.

4. Delete the saved query in the admin. The run stays, its saved query is now empty, and `effective_params` has not changed.

Open the admin at `http://127.0.0.1:...` and the UI at `http://localhost:...` (or the other way round). Common errors explains why.

## Common errors

- **`403` with "CSRF Failed" when clicking Start run.** You are logged into `/admin` on the same host as the UI. Browsers share cookies across ports, so the admin login reaches the API, and DRF then requires a CSRF token the UI does not send. Use different hosts as above, or log out of the admin.

- **`404` "No SavedQuery matches the given query."** The query is in another project, or was created by another user, or no longer exists.

- **`400` listing parameter messages.** The query's stored parameters break a YouTube rule. Fix the query, then start again.

## Known gaps

- The CSRF problem above is older than this story; every UI POST has it. It is logged in `deferred-work.md` together with the missing authentication setup.

- In development, if Vite hot-reloads the page while a start request is in flight, the card can stay on "Starting…" until you refresh. The review rejected a fix as not worth the extra branch.

- `App.tsx` has no automated render tests, so the button is checked by hand.
