# 14 - Discover videos with YouTube search.list

Story: US-015, Discover videos with YouTube search.list.

Status note: this document describes the US-015 implementation **after** the code review of 2026-10-05 and the fixes that followed it.

## What this story added

Until now a started run stayed `pending` forever: nothing executed it. This story adds the collector, the first code that actually talks to YouTube.

- `manage.py collect_runs`, a command that collects every `pending` run, oldest first.

- `collect_run`, in `src/api/core/collection.py`, which does the work for one run.

- two new tables: `youtube_videos` (one row per video, shared by every run that finds it) and `collection_run_videos` (which run found which video, on which search page).

For each run, the collector:

1. claims the run by moving it from `pending` to `running`.

2. calls YouTube's `search.list` through `call_youtube` (US-013), using the parameters the run copied from its saved query (US-011).

3. stores each video found and links it to the run.

4. asks for the next page until it has enough videos, then marks the run `completed`, or `failed` with the reason.

## Why this matters

This is where the thesis's dataset starts: the list of videos a query found. Because every request goes through `call_youtube`, each page is logged with its parameters and quota cost, and the run's totals (US-012) stay current. A reader can therefore see what was found and exactly how.

## Key concept: a management command instead of a background worker

A management command is a script Django runs on demand: `python manage.py collect_runs`. It was chosen over two alternatives:

- **Collecting inside the web request** would tie up a Gunicorn worker for several slow YouTube calls, against its 60-second timeout.

- **A job queue** (Celery and similar) would need a new dependency and a broker service.

The cost is that the UI shows `pending` until someone runs the command. That is fine for a local research tool, and the command can be scheduled later if needed.

## Key concept: claiming a run safely

The first step is `run.transition_to("running")`, which is a compare-and-set from US-010: it only succeeds if the row is still `pending`. Two consequences follow:

- running `collect_runs` twice never collects a run twice. The second time, the run is no longer `pending`.

- if two copies of the command ran at once, only one would win each run. The other gets a `ValueError` and skips it.

## Key concept: not wasting quota

Each `search.list` page costs 100 quota units, out of a default daily quota of 10,000. So the collector stops as early as it can:

- each page asks only for the videos still needed. With a cap of 60 and pages of 50, the second request asks for `maxResults=10`, not 50.

- paging stops when the cap is reached, when YouTube sends no `nextPageToken`, or when a page comes back empty.

- a saved query with **no cap** (`max_videos_to_discover` empty) fetches exactly one page, even if YouTube offers more.

## Key concept: one video, many runs

`youtube_videos.youtube_video_id` is unique. When a later run finds a video that is already stored, the row is **reused**, not duplicated. Its `title` and `last_fetched_at` are refreshed, because search just re-fetched it.

`last_fetched_at` matters for retention: the 30-day purge (US-040) deletes videos whose `last_fetched_at` is older than 30 days, and the links go with them (`CASCADE`). The run itself and its counts are kept.

If the same video shows up twice within one run, for example on two pages, it is linked once and counted once in `total_videos_discovered`.

## Key concept: HTML-escaped text from YouTube

`search.list` returns titles and descriptions HTML-escaped: `Rock &amp; roll isn&#39;t dead`. The collector runs them through Python's `html.unescape` before storing, so the database holds `Rock & roll isn't dead`. The code review caught this.

## File-by-file explanation

### `src/api/core/models.py`

- `YouTubeVideo`: `youtube_video_id`, `title`, `description`, `youtube_published_at`, `live_broadcast_content`, `last_fetched_at`, `created_at` and `updated_at`. The rest of the columns in `docs/database_schema.md` (tags, duration, channel, raw payload and others) come with US-017 and US-018, which call `videos.list` and `channels.list`.

- `CollectionRunVideo`: the run, the video, `page_number` and `discovered_at`. The pair (run, video) is unique.

### `src/api/core/migrations/0008_youtubevideo_collectionrunvideo.py`

Generated by `makemigrations`. Creates both tables.

### `src/api/core/collection.py`

- `collect_run(run, *, api_key, transport=None)`: claims the run, runs discovery, and sets the final status.

- `_discover_videos`: the paging loop. When it finishes, even after a failure, it writes `total_videos_discovered` as the number of distinct links.

- `_search_params`: checks that the run's `effective_params` have the expected shape before using them.

- `_store_video`: turns one search result into a `YouTubeVideo`, using `update_or_create`. A result with no video ID is skipped.

### `src/api/core/management/commands/collect_runs.py`

The command. It refuses to start without `YOUTUBE_API_KEY`, then prints one line per run: `<run id>: completed, 60 videos`.

### `src/api/core/admin.py`

A shared `ReadOnlyAdmin` base (no add, change or delete) is now used for request logs, videos and run-video links. These rows are collection evidence.

### `src/api/core/tests.py`

`CollectRunTests` uses a fake transport that serves search pages by `pageToken`. It covers:

- the happy path, including the shrinking last page
- the last page, an empty page and a run with no cap
- duplicates, and reuse of a known video
- an API failure and an unexpected error
- skipping runs that are not pending
- escaped titles
- the command itself: oldest first, only once, and the missing key

## How the pieces connect

```text
manage.py collect_runs
   |-- no YOUTUBE_API_KEY? --> CommandError, nothing touched
   '-- for each pending run, oldest first: collect_run(run)
          |-- transition_to("running")      (not pending? skip)
          |-- loop:
          |     call_youtube(run, "search.list", search_list + maxResults + pageToken)
          |        --> ApiRequestLog row, run totals +1 request / +100 quota
          |     for each item: YouTubeVideo (create or refresh) + CollectionRunVideo
          |     stop at cap / no nextPageToken / empty page / no cap after page 1
          |-- total_videos_discovered = distinct links
          '-- transition_to("completed")
              or transition_to("failed", error_message="HTTP 403: quotaExceeded")
```

## How to test manually

This spends real quota, so put a real key in `src/api/.env` (`YOUTUBE_API_KEY=...`).

1. In the UI, save a query with **Videos** set to 60, then click **Start run**. The card shows `Run pending`.

2. Run `venv/bin/python manage.py collect_runs` from `src/api`. It prints something like `<run id>: completed, 60 videos`.

3. In `/admin/`, open the run. Its status is `completed`, the totals are 2 requests and 200 quota units, and `total_videos_discovered` is 60.

4. Open Api request logs. There are two `search.list` rows: the first with `maxResults` 50, the second with 10.

5. Open Collection run videos. There are 60 links, on pages 1 and 2.

6. Run the command again. It prints nothing, because no run is pending.

## Common errors

- **`CommandError: YOUTUBE_API_KEY is not configured.`** Add the key to `src/api/.env`.

- **The run ends `failed` with `HTTP 403: quotaExceeded`.** The daily quota is used up. Videos found before the failure stay linked, and the request log shows which page failed.

- **The run ends `failed` with `HTTP 400: keyInvalid` (or similar).** The key is wrong, or the YouTube Data API is not enabled for it in Google Cloud.

- **The UI still says `pending`.** The collector only runs when you run the command.

## Known gaps

- If the process crashes after claiming a run, the run stays `running` forever. Nothing recovers it yet.

- One malformed search result (for example an impossible date) fails the whole run instead of being skipped. Real YouTube data does not do this, so the review left it.

- No duplicate count is stored yet. US-016 adds it with the discovery summary.
