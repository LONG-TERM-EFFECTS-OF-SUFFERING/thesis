# 13 - Store collection run counts, quota, timestamps and errors

Story: US-012, Store collection run counts, quota, timestamps and errors.

Status note: this document describes the US-012 implementation **after** the code review of 2026-10-05 and the fixes that followed it. US-012 was built after US-013, so it builds on the request log and `call_youtube` from [page 12](12-create-api-request-log-model-and-service-wrapper.md).

## What this story added

A run could already say *whether* and *when* it ran (US-010). This story lets it say *how much* and *what went wrong*. `CollectionRun` gains seven columns:

| column | filled by |
| :-- | :-- |
| `total_api_requests` | `call_youtube`, once per request |
| `total_quota_units` | `call_youtube`, the endpoint's quota cost per request |
| `total_videos_discovered` | nothing yet (US-015) |
| `total_videos_collected` | nothing yet (later collection stories) |
| `total_comments_collected` | nothing yet (comment stories) |
| `total_replies_collected` | nothing yet (comment stories) |
| `error_message` | `transition_to("failed", error_message=...)` |

The "timestamps" in the story title were already there: `started_at` and `finished_at` from US-010.

The new fields appear, read-only, in the run's API response and in the Django admin. The UI did not change.

## Why this matters

When a run fails or returns fewer videos than expected, a researcher needs to explain it: "the run made 12 requests, spent 1,100 quota units and failed with `HTTP 403: quotaExceeded`". These columns are that explanation, and like the rest of the run record they are kept after the 30-day purge of YouTube data.

## Key concept: a total kept in step with the logs

The request and quota totals could be computed from the request logs every time. Instead they are stored on the run, as `docs/database_schema.md` specifies, so reading a run needs no extra query. The price is that the same fact now lives in two places, so the code has to keep them in step. It does so in three ways:

1. **One writer.** Only `call_youtube` changes these two totals.

2. **One transaction.** The log row and the totals update are written inside `transaction.atomic()`. Either both are saved or neither is, so a crash can never leave a log row the totals did not count. The HTTP request itself runs **after** that block, so the database is not held open while waiting for YouTube.

3. **An update done by the database.** The increment is written as:

```python
CollectionRun.objects.filter(pk=run.pk).update(
    total_api_requests=F("total_api_requests") + 1,
    total_quota_units=F("total_quota_units") + log.quota_cost,
)
```

`F("total_api_requests") + 1` means "add one to whatever value is in the row right now", and PostgreSQL does it in one statement. The tempting alternative, `run.total_api_requests += 1; run.save()`, reads the value into Python first. If two calls do that at the same time from copies of the same run, both read 5 and both write 6, and one request is lost. A test uses an out-of-date copy of the run to prove the `F()` version does not lose it.

After the update, `call_youtube` refreshes the two fields on the caller's `run`, so the caller sees the new totals.

## Key concept: failed calls still count

The totals are increased when the request is logged, before it is sent. A call that fails with `HTTP 403` still adds its cost, because YouTube charges failed requests too.

A call that never reaches YouTube (a DNS failure, say) is counted as well. The review accepted this on purpose. The log row keeps the full cost for every failed call (a US-013 decision), so the totals still equal the sum over the logs, and over-counting is the safer error when the number is used to budget quota.

## Key concept: a failed run must say why

`transition_to` (from US-010) is still the only way to change status. It now takes an optional `error_message`:

```python
run.transition_to("failed", error_message="HTTP 403: quotaExceeded on search.list")
```

- Moving to `failed` **requires** a message that is not blank. `None`, `""` and `"   "` all raise `ValueError`.

- Passing a message for any other status also raises `ValueError`. Only failed runs carry an error.

- The legality check runs first, so an illegal move keeps its usual message, `Cannot move collection run from 'pending' to 'failed'.`

- The message is written in the same compare-and-set `UPDATE` as the status, so they can never disagree.

## File-by-file explanation

### `src/api/core/models.py`

Adds the seven fields to `CollectionRun` after `finished_at`, and the `error_message` rules to `transition_to`.

### `src/api/core/migrations/0007_collectionrun_totals_and_error_message.py`

Generated by `makemigrations`, then renamed to a readable name. Adds the seven columns.

### `src/api/core/youtube_client.py`

`call_youtube` now creates the log row and increments the totals inside one `transaction.atomic()` block, then refreshes `run`.

### `src/api/core/serializers.py` and `src/api/core/admin.py`

List the new fields. They are read-only in both, so no client and no admin user can change them by hand.

### `src/api/core/tests.py`

- `CollectionRunModelTests`: defaults, failing with a message, failing without one (`None`, `""`, `"   "`), a message on another status, and illegal moves with or without a message.

- `CallYouTubeTests`: totals after two successful calls (101 units for `search.list` plus `videos.list`, using an out-of-date copy of the run), after a 403, and unchanged after a rejected call.

- `CollectionRunStartApiTests`: the new fields are in the 201 response, at 0 and `null`.

## How the pieces connect

```text
call_youtube(run, endpoint, params, ...)
   |-- reject bad input --> ValueError (no log, no totals)
   |-- transaction.atomic():
   |      |-- ApiRequestLog.objects.create(... quota_cost ...)
   |      '-- UPDATE collection_runs
   |             SET total_api_requests = total_api_requests + 1,
   |                 total_quota_units  = total_quota_units + quota_cost
   |-- run.refresh_from_db(totals)
   '-- send the request (outside the transaction)

collector (US-015, later), when something goes wrong:
   run.transition_to("failed", error_message="HTTP 403: quotaExceeded")
```

## How to test manually

Start a run from the UI, then in the Django shell (`venv/bin/python manage.py shell`):

```python
from core.models import CollectionRun
from core.youtube_client import call_youtube
run = CollectionRun.objects.first()
fake = lambda url: (200, {"items": []})
call_youtube(run, "search.list", {"part": "snippet", "q": "test"}, api_key="test", transport=fake)
run.total_api_requests, run.total_quota_units   # (1, 100)
run.transition_to("running")
run.transition_to("failed", error_message="manual test")
```

Then open the run in `/admin/`: the totals read 1 and 100, the error message reads `manual test`, and every new field is read-only.

## Common errors

- **`ValueError: A failed collection run needs an error message.`** You called `transition_to("failed")` without `error_message`, or with a blank one. Say why it failed.

- **`ValueError: An error message is only stored when a run fails, not 'completed'.`** Only `failed` takes a message.

- **Totals look too high after network trouble.** Requests that never reached YouTube are counted too, by design. The request logs show which calls had no HTTP status.

## Known gaps

- The video and comment counters stay at 0 until the stories that collect videos and comments fill them.

- A request that failed before reaching YouTube is counted at full cost. This is a deliberate conservative over-count, explained above.
