# 10 - Create collection run model and status lifecycle

Story: US-010, Create collection run model and status lifecycle.

Status note: this document describes the US-010 implementation **after** the code review of 2026-10-05 and the fixes that followed it.

## What this story added

Until now the app could only describe a collection: a project and a saved query. Nothing recorded an **attempt** to collect. This story adds that record, the `CollectionRun` model, stored in the `collection_runs` table.

A run stores:

- the project it belongs to, the saved query that launched it and the user who started it.

- a status: `pending`, `running`, `completed`, `failed` or `cancelled`.

- `started_at` and `finished_at`, set automatically by the status changes.

- `data_purged_at`, empty for now. US-040 fills it when the 30-day purge deletes the YouTube data the run collected.

- `created_at`.

There is no endpoint and no screen yet. US-011 starts a run from a saved query; this story only provides the record and its rules.

## Why this matters

The thesis promises that a reader can trace every dataset back to how it was obtained. The first question that trace has to answer is simple:

```text
Was this dataset collected successfully, from which query, and when?
```

The run record answers it, and later stories hang everything else on it: request logs (US-013), counts and quota (US-012), discovered videos (US-015). Runs are methodological records, so they are **kept** after the 30-day purge of YouTube data; only `data_purged_at` changes.

## Key concept: a status lifecycle

A lifecycle is the list of allowed status changes. Here it is:

```text
pending --> running --> completed
   |           |------> failed
   |           '------> cancelled
   '------------------> cancelled
```

`completed`, `failed` and `cancelled` are **terminal**: nothing leaves them. A finished run that could flip back to `running` would make its own timestamps lie.

The whole lifecycle is one dictionary on the model, `ALLOWED_TRANSITIONS`. It maps each status to the set of statuses it may move to. No state-machine library is needed for five states.

## Key concept: one method owns every status change

Code never writes `run.status = ...` directly. It calls `run.transition_to("running")`. That method:

1. checks the move against `ALLOWED_TRANSITIONS` and raises `ValueError` if it is not allowed, for example `Cannot move collection run from 'pending' to 'completed'.`

2. sets `started_at` when entering `running`, or `finished_at` when entering a terminal status.

3. writes to the database **only if the row still has the old status**.

Point 3 came from the code review. Imagine two copies of the same run loaded in memory, both saying `pending`. One copy moves the run to `running` and then `completed`. The other copy still believes it is `pending` and asks for `cancelled`. Without point 3 it would overwrite a finished run. With it, the database update matches zero rows and the method raises `ValueError` instead. This pattern is called **compare-and-set**: "change it to X, but only if it is still Y".

## Key concept: rules the database enforces itself

Two `CheckConstraint`s live in PostgreSQL, so even code that skips `transition_to` cannot store nonsense:

- `collection_run_status_allowed`: the status is one of the five values.

- `collection_run_finished_after_started`: `finished_at` is never earlier than `started_at` when both are set.

## File-by-file explanation

### `src/api/core/models.py`

Adds `CollectionRun` after `ResearchProject`, with `RunStatus` choices, `ALLOWED_TRANSITIONS`, `TERMINAL_STATUSES`, the two constraints and `transition_to`.

The links use different delete rules on purpose:

- `project` is `CASCADE`: deleting a project deletes its runs.

- `saved_query` and `initiated_by_user` are `SET_NULL`: deleting a query or a user keeps the run, with the link emptied. The run is audit evidence; it should outlive what launched it. They also have `blank=True`, so the admin form accepts a run whose link was emptied.

### `src/api/core/migrations/0004_collectionrun.py`

Generated by `makemigrations`. Creates the table and both constraints.

### `src/api/core/admin.py`

Registers the model in Django admin for local inspection. `status` and the timestamps are read-only there, so admin cannot bypass `transition_to` either.

### `src/api/core/tests.py`

`CollectionRunModelTests` covers: the defaults of a new run, starting, finishing in each terminal status, cancelling before start, every illegal move (including every move out of a terminal status), the stale-copy case, both database constraints, that the constraints exist on the table, and that deleting a saved query keeps the run.

## How the pieces connect

```text
ResearchProject 1 ----< CollectionRun >---- 0..1 SavedQuery
                            |
                            +-- status, changed only by transition_to()
                            |       |
                            |       +--> ALLOWED_TRANSITIONS check
                            |       +--> stamps started_at / finished_at
                            |       +--> UPDATE ... WHERE status = <old status>
                            |
                            +-- PostgreSQL checks: allowed status, finished >= started
```

Later stories add to this picture: US-011 creates runs, US-012 adds counts and quota, US-013 links request logs to a run.

## How to test manually

In the Django shell (`venv/bin/python manage.py shell`):

```python
from core.models import CollectionRun, SavedQuery
q = SavedQuery.objects.first()
run = CollectionRun.objects.create(project=q.project, saved_query=q)
run.transition_to("running")
run.started_at          # now set
run.transition_to("completed")
run.finished_at         # now set
run.transition_to("running")   # ValueError: Cannot move collection run from 'completed' to 'running'.
```

Then open `/admin/` and check the run: `status` and the timestamps are shown but cannot be edited.

## Common errors

- **`ValueError: Cannot move collection run from 'pending' to 'completed'.`** The move is not in `ALLOWED_TRANSITIONS`. Start the run first.

- **The same `ValueError` for a move that looks allowed.** Your copy of the run is stale: the row changed after you loaded it. Call `run.refresh_from_db()` and decide again.

- **`IntegrityError` mentioning `collection_run_status_allowed` or `collection_run_finished_after_started`.** Something wrote the row directly with a bad status or inverted timestamps. Use `transition_to`.
